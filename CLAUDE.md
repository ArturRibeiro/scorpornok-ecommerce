# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Visão geral

Scorponok é um backend de e-commerce modular em .NET, feito para estudo e demonstração (DDD, CQRS, MediatR, domain notifications, integration events com outbox). Todos os projetos da solution são **net10.0** (`<TargetFramework>` vem do `Directory.Build.props`). Comentários no código, os casos de uso (`usecases/`, um arquivo por caso de uso; os de conta do cliente têm o prefixo `Login-`) e parte da documentação estão em português.

## Comandos

```bash
dotnet build Scorponok.slnx                    # compila tudo (CI: restore → build → test no master)
dotnet test Scorponok.slnx                     # roda todos os testes
dotnet test src/backend/Frameworker/Programming.Functional.Tests   # um projeto de teste
dotnet test src/backend/Frameworker/Programming.Functional.Tests --filter "FullyQualifiedName~OptionTests"  # uma classe/teste
dotnet run --project src/backend/Catalog/Catalog.Web.Api           # sobe a API de Catalog (precisa dos bancos do compose)
dotnet run --project src/backend/Gateway/Gateway.Web.Api           # sobe o gateway GraphQL em 5200 (usa o Catalog em localhost:5064)
./scripts/compose-gateway.sh                   # exporta o schema dos subgraphs e recompõe os .far do gateway (rode ao mudar um schema)
dotnet run --project src/backend/Store/Orders.Web.Api              # sobe a API de Orders (precisa dos bancos, do RabbitMQ e do Mailpit do compose)
dotnet run --project src/backend/Payments/Payments.Web.Api         # sobe a API de Payments (precisa dos bancos e do RabbitMQ do compose)
dotnet run --project src/backend/Customers/Customers.Web.Api       # sobe a API de Customers (precisa dos bancos, do RabbitMQ e do Keycloak do compose)
docker compose up -d --build                   # Gateway GraphQL (5200), Catalog (5064), Orders (5224), Payment (5220) e Customers (5230), cada um com seu Postgres 16, o RabbitMQ, o Mailpit, o Keycloak (8080) e o front-end (3000); Swagger em /swagger
docker compose -f docker-compose.database.yml up -d   # só os bancos (o docker-compose.yml raiz inclui este arquivo)
docker compose -f docker-compose.messaging.yml up -d  # só o RabbitMQ (5672; painel em http://localhost:15672, guest/guest)
docker compose -f docker-compose.mail.yml up -d       # só o Mailpit (SMTP 1025; caixa de entrada em http://localhost:8025)
docker compose -f docker-compose.identity.yml up -d   # só o Keycloak e o seu banco (console em http://localhost:8080, admin/admin)
docker compose -f docker-compose.frontend.yml up -d --build   # só o front-end (também incluído pelo docker-compose.yml)
```

- Cada projeto `*.Web.Api` tem um arquivo `.http` para testar os endpoints.

## Versões de pacotes

Todas as versões de pacotes são propriedades MSBuild no `Directory.Build.props`, por exemplo `Version="$(MediatR)"` (EF Core 10, Npgsql 10, MediatR 13, MassTransit 8.5, Swashbuckle 10). Adicione ou atualize versões lá, nunca direto no csproj. O mesmo arquivo define o `<TargetFramework>` (`net10.0`) e o `LangVersion`, e os projetos usam `<TargetFramework>$(TargetFramework)</TargetFramework>`. O CI (`.github/workflows/dotnet.yml`) instala o SDK `10.0.x`; não há `global.json`.

## Arquitetura

Os bounded contexts ficam em `src/backend/` (`src/frontend/` contém o front-end React + Vite, com seu próprio `CLAUDE.md`). Cada um é dividido em projetos por camada, e as dependências apontam para dentro, até o Domain:

- **Catalog** (lado de leitura / queries): `Catalog.Domain` (entidade `Product`, com `Brand`) ← `Catalog.Queries` (`IProductQueries`, com `QueryProducts()`, a consulta ordenada por `Id` que o REST e o GraphQL compartilham, `SearchProducts(ProductSearch, PagingModel)` e `GetBrands()` (busca, `add-product-search`: cada palavra do termo precisa aparecer em `Name`, `Brand` ou `Description`, em qualquer ordem, por `ILIKE` sobre `unaccent` dos dois lados (`EF.Functions.ILike`/`Unaccent`, com `%`, `_` e `\` escapados; predicados montados palavra a palavra em `ProductSearchExpressions`; a extensão `unaccent` vem do `HasPostgresExtension` no `ApplicationCatalogDbContext` e o `EnsureCreated` a cria); ordem por grupo (todas as palavras no nome, depois no nome ou na marca, depois com a descrição) e então `Id`; marcas e faixa de preço com os limites incluídos; termo até 100 caracteres e 10 palavras; mínimo acima do máximo devolve página vazia; mesmas regras do `PagingModel`), `IApplicationCatalogDbContext`, paginação via `ToPagedList`/`IPagedList` do `Frameworker.EntityFrameworkCore`) ← `Catalog.Infrastructure` (`ApplicationCatalogDbContext`, configurações do EF, `AddInfrastructure`) ← `Catalog.Web.Api` (REST e, em `GraphQL/`, o subgraph `catalog` do gateway).
- **Gateway** (GraphQL federado, `add-graphql-gateway`): `Gateway.Web.Api` é o ponto de entrada GraphQL único da loja (`/graphql`, porta 5200), com o Hot Chocolate Fusion 16 (versão em `$(HotChocolate)` no `Directory.Build.props`; a ferramenta `nitro` vem do `dotnet-tools.json` da raiz). Subgraphs: Catalog, Customers, Orders e Payments. Catalog: `products(page, pageSize)` sobre o `GetAllProducts(PagingModel)` do REST (mesmo `pageInfo`, mesmos ajustes: tamanho acima de 20 vira 20, sem erro) e `productById(id)` com `[Lookup]` (nulo se não existe); `searchProducts(term, brands, minPrice, maxPrice, page, pageSize)` (busca no nome, na marca e na descrição, sem diferenciar maiúsculas e acentos, os do nome primeiro, com o mesmo `ProductPage`; sem filtros, o catálogo inteiro; as sugestões da loja são a mesma consulta com `pageSize: 5`) e `productBrands` (marcas em ordem alfabética). A busca não existe no REST. O subgraph usa `AddGraphQLServer("catalog")`, `MapGraphQL(schemaName: "catalog")` e `RunWithGraphQLCommandsAsync` (o `schema export` roda antes da seed, sem banco). A composição é versionada: `schema.graphqls` e `schema-settings.json` (nome `catalog` e o endereço por ambiente em `environments`: `local` → `localhost:5064`, `compose` → `catalog-api:8080`) no `Catalog.Web.Api`, e `gateway.local.far`/`gateway.compose.far` no gateway, todos gerados por `scripts/compose-gateway.sh` (`schema export` + `nitro fusion compose --env`); o gateway carrega o de `Fusion:Archive` (o compose usa o `gateway.compose.far`). Limites (seção `GraphQL`, validados na partida): `MaxDepth` (8, `AddMaxExecutionDepthRule`, sem contar a introspecção) e `MaxFields` (200, `MaxFieldsRule`: campos por operação com fragmentos expandidos, porque o Fusion não calcula custo no gateway), recusados na validação, sem chamar os subgraphs; introspecção só em Development (política padrão do Fusion). O cliente HTTP `fusion` tem timeout de 5 s; subgraph fora vira erro só no campo (`200` com `errors`). `/health/live` e `/health/ready` (só o `.far` carregado, `FusionSchemaHealthCheck`). O REST do Catalog continua (o Orders usa o `GetProductsByIds`). **Autenticação** (`add-customers-subgraph`, `Gateway.Web.Api/Authentication/`): o gateway valida o JWT do Keycloak (seção `Keycloak`, audience `gateway-api`, no compose com `MetadataAddress` em `keycloak:8080`) e o `RejectInvalidCredentials` responde `401` a token inválido, expirado ou de outro audience, sem chamar os subgraphs; sem token, a consulta segue (o catálogo é público). O `AuthorizationForwardingHandler` (no cliente `fusion`) repassa o `Authorization` da loja a cada subgraph, que valida de novo com o seu audience e aplica a regra de acesso: o gateway não aplica o `@authorize` do schema composto. Customers (subgraph `customers`, `Customers.Web.Api/GraphQL/`): `me: CustomerProfile!` e `updateMyProfile(input: UpdateMyProfileInput!): UpdateMyProfilePayload!` (`profile` nulo e `errors: [FieldError { field, messages }]` nas chaves de sempre, `cpf`, `address.zipCode`), com `[Authorize(Policy = VerifiedCustomer)]` do `HotChocolate.AspNetCore.Authorization`: sem login → `AUTH_NOT_AUTHENTICATED`, sem e-mail confirmado → `AUTH_NOT_AUTHORIZED`. Os campos do input são opcionais para que a falta de um vire erro do campo. `me` não é nulo: numa consulta que o junte ao catálogo, o erro de acesso anula a resposta inteira, por isso a loja consulta separado. O REST `/customers/me` continua. Orders (subgraph `orders`, `add-orders-subgraph`, `Orders.Web.Api/GraphQL/OrderGraph.cs`), sobre os mesmos handlers do REST e com o mesmo `[Authorize(Policy = VerifiedCustomer)]`: `myOrders(page, pageSize)` e `myOrder(orderNumber)` (nulo para pedido de outro cliente ou inexistente), `placeOrder(input: PlaceOrderInput!)` (endereço, comprador, itens só com `productId` e `units` e o token do cartão; cliente e e-mail do token; sem endereço, um vazio, para a falta virar mensagem) e `retryOrderPayment(input: RetryOrderPaymentInput!)`. Os desfechos viram `errors: [UserError { code, message }]` no payload (`OrderErrorCodes`): `VALIDATION` (pedido inválido, sem cartão), `CATALOG_UNAVAILABLE`, `NOT_FOUND` e `CONFLICT`, com as mensagens de hoje. O hub `/hubs/orders` (SignalR) e o REST continuam. Como o `placeOrder` consulta o Catalog com limite de 5 s, o cliente `fusion` do gateway tem timeout de 15 s. Payments (subgraph `payments`, `add-payments-subgraph`, `Payments.Web.Api/GraphQL/CardTokenGraph.cs`): `tokenizeCard(input: TokenizeCardInput!): TokenizeCardPayload!` (`token { token last4 expiresAt }` ou `errors: [CardFieldError { field message }]`, com os campos do formulário), sobre o mesmo `CreateCardTokenCommand` do REST e sem login. Só tem mutation, por isso o schema usa `StrictValidation = false` (sem tipo `Query`). **Decisão de segurança**: o cartão (número, validade e CVV) passa pelo gateway; ele não pode ser registrado em lugar nenhum no caminho. O gateway define `IncludeExceptionDetails = false` e `CollectOperationPlanTelemetry = false` explicitamente, não liga log de requisição (`HttpLogging`), e o `CardDataTests` do `Gateway.Tests` tokeniza com o Payments fora, em Development e Production, captura todos os logs (com filtro próprio, acima dos do `appsettings`) e falha se o número ou o CVV aparecerem no log ou na resposta. O `TokenizeCardInput` e o comando não mostram o cartão no `ToString()`.
- **Store / Orders** (lado de escrita / commands): `Orders.Domain` (agregado `Order` com `ConfirmPayment`/`FailPayment`, que só agem sobre pedido `Pending`, e `Email`, e o `OrderPayment` (1:1, tabela `OrderPayment` com chave `OrderId`, criado vazio com o pedido) com `PaymentId` e `EmailSentAt`, alterado só pelo `Order` (`ConfirmPayment`, `MarkPaymentEmailSent`); validadores FluentValidation; `IOrderRepository` com `GetByNumberAsync` e `GetAwaitingPaymentEmailAsync`) ← `Orders.CommandHandlers` (`IRequestHandler`s do MediatR: o `OrderHandler` monta um `Order` com o `OrderBuilder` fluente, valida com `IsValid()` (e o comprador, `OrderBuyer`, com as regras de `Shared.Code/Validation`), salva e publica, pelo outbox, o `OrderPlaced` (para o Customers) e o `PaymentRequested`; `OrderPaymentHandlers` aplica o resultado do pagamento e chama o `IOrderPaymentNotifier`; `IOrderEmailSender` e o texto do e-mail em `OrderPaymentEmail`) ← `Orders.Infrastructure` (`OrderContext`, repositório, consumidores `PaymentApproved`/`PaymentRejectedConsumer`, MassTransit, e-mail em `Email/` — `SmtpOrderEmailSender` com MailKit e o `OrderEmailDispatcher` — e DI em `AddInfrastructure`) ← `Orders.Web.Api` (endpoints, o hub SignalR `OrderHub` e a autenticação em `Authentication/`: `CustomerIdentity` e a política `VerifiedCustomer`). O Orders não tem código de pagamento; o `Order` guarda só o `PaymentId`, no `OrderPayment`.
- **Payments**: `Payments.Domain` (agregado `Payment`, que guarda só os 4 últimos dígitos do cartão e nunca o CVV, com `Status` `Processing`/`Approved`/`Rejected`, `Attempt` e a chave de idempotência `IdempotencyKey` = `"{OrderNumber}-{Attempt}"`, hoje sempre tentativa 1; `Payment.Start` cria em processamento e `Complete(PaymentResult)` só age sobre ele; `IPaymentGateway` com o contrato "mesma chave, mesma resposta, sem nova cobrança", `PaymentRequest` com `IdempotencyKey`, `PaymentResult`, `IPaymentRepository.GetByIdempotencyKeyAsync`) ← `Payments.CommandHandlers` (`ProcessPaymentCommand` e handler: busca pela chave; se não existe, resolve o `CardToken` da mensagem — desconhecido, vencido ou já usado vira pagamento `Rejected` com o motivo `Token do cartão inválido ou vencido.`, sem gateway e sem erro; válido é marcado como usado (`UsedAt`, token de concorrência no EF: o mesmo token em duas cobranças simultâneas falha na segunda, que a retentativa recusa) na mesma gravação do pagamento —, grava `Processing` **antes** de cobrar; se está `Processing`, cobra no gateway com a chave e completa; publica `PaymentApproved`/`PaymentRejected`, também quando o pagamento já estava completo. Uma reentrega depois de cobrar e antes de gravar o resultado recebe do gateway a resposta original, e duas entregas simultâneas esbarram no índice único: a segunda falha, e a retentativa do MassTransit encontra o registro da primeira) ← `Payments.Infrastructure` (`PaymentContext` no schema `payment`, índice único em `IdempotencyKey` (e índice comum em `OrderNumber`); `PaymentRepository`; `PaymentGateway` stub, `Singleton`, que recusa cartão terminado em `0000` e guarda o resultado por chave em memória (as chaves se perdem ao reiniciar); consumidor `PaymentRequestedConsumer`; MassTransit e DI em `AddInfrastructure`; e o event store antigo, `EventStoreContext`/`SqlEventStore`, sem uso) ← `Payments.Web.Api` (consome as mensagens e expõe a tokenização do cartão, como o cofre de um gateway real: a mutation `tokenizeCard` do subgraph `payments` (`add-payments-subgraph`), que a loja chama pelo gateway GraphQL, e o `POST /card-tokens`, o REST de antes, que continua. Valida como o checkout (`CardValidation`, erros por campo) → `400 { errors }`, ou grava um `CardToken` (`tok_…`, titular, `Last4`, validade, `ExpiresAt` em 24 h, `UsedAt`; tabela `CardTokens`, sem número completo nem CVV) → `201 { token, last4, expiresAt }`. O CVV só é conferido em memória e não é logado. Sem autenticação: o token sozinho não cobra nada e só vale num pedido autenticado).
- **Customers** (cadastro do cliente): `Customers.Domain` (agregado `Customer`, com `Id` = `sub` do Keycloak, `Email` copiado do token a cada gravação, `FullName`, `Phone`, `Cpf` e o value object `Address` (`Street`, `Number`, `Complement`, `District`, `City`, `State`, `ZipCode`), telefone, CPF e CEP só com dígitos; `CustomerValidator`/`AddressValidator`: tudo obrigatório menos o complemento, erros por campo nas chaves do JSON (`cpf`, `address.zipCode`; sem endereço, `address`); `DeliveryAddress`, o histórico de endereços de entrega; `ICustomerRepository`) ← `Customers.CommandHandlers` (`GetCustomerProfileQuery` (sem cadastro, só o e-mail), `UpdateCustomerProfileCommand` (upsert, valida antes de gravar) e `RecordPurchaseCommand`/`RecordPurchaseHandler`: grava o endereço do pedido no histórico (ignora pedido já gravado) e, se o cliente não tem cadastro, cria um com o comprador e esse endereço; um cadastro existente nunca muda pela compra) ← `Customers.Infrastructure` (`CustomerContext` no schema `customer`, tabelas `Customers` e `DeliveryAddresses` (índice único em `OrderNumber`), `CustomerRepository`, consumidor `OrderPlacedConsumer` (fila `order-placed`) com `UseTransientRetry`, MassTransit e DI em `AddInfrastructure`) ← `Customers.Web.Api` (`GET`/`PUT /customers/me` com a política `VerifiedCustomer`; a autenticação em `Authentication/` é cópia da do Orders, com `Audience` `customers-api` e sem o `access_token` na query). Corridas (mesma mensagem duas vezes, duas primeiras compras ao mesmo tempo) caem no índice único ou na chave `sub`, e a retentativa relê.
- **Shared/Shared.Code**: os blocos básicos de DDD/CQRS. São eles `Entity<T>` (acumula erros de validação), `ValueObject`, `IAggregateRoot`, `IRepository`/`IUnitOfWork`, `Message`/`CommandBase`/`Event`, a base `CommandHandler` e `DomainNotification` com seu handler. Também tem `IMemoryBus`/`MemoryBus`, um wrapper fino sobre o `IMediator`: `SendAsync` para commands sem retorno (`Message`) e `RequestAsync` para commands com resposta (`Message<TResponse>`). O `RaiseEvent` está comentado (não faz nada). Em `IntegrationEvents/` ficam os contratos trocados entre contextos pelo RabbitMQ (`PaymentRequested`, `PaymentApproved`, `PaymentRejected`, e o `OrderPlaced` com o `ShippingAddress`, do Orders para o Customers) e o `IIntegrationEventPublisher`, que os handlers usam para publicar sem depender do MassTransit. Em `Validation/` ficam as regras de CPF, telefone, UF, CEP e nome (`Cpf`, `Phone`, `BrazilianState`, `ZipCode`, `PersonName`, com `Normalize` que tira só a pontuação aceita), usadas pelo Customers e pelo Orders.
- **Frameworker**: infraestrutura reutilizável. `Programming.Functional` fornece `Result`/`Result<T>`/`Maybe<T>`/`Option<T>`. `Frameworker.EntityFrameworkCore` fornece paginação. `Frameworker.Integration.Tests` fornece bases de `WebApplicationFactory` com Testcontainers (Postgres/Oracle/Sqlite), que escolhem o `appsettings.<dbtype>.json`.

### Convenções das Web APIs

- Minimal APIs: os endpoints são métodos de extensão de `WebApplication` em `WebApplicationExtensions/` (ex.: `app.GetAllProducts()`, `app.CreateOrder()`), chamados no `Program.cs`.
- Os commands chegam aos handlers assim: endpoint ou consumidor do MassTransit → `IMemoryBus.SendAsync(command)` (ou `RequestAsync`, quando o handler devolve um resultado) → MediatR → handler. Os handlers são registrados explicitamente em cada `Infrastructure/Extensions/ServiceCollectionExtensions.cs`, junto com o scan do assembly.
- **A connection string (`ConnectionStrings:ConnectionString`) é obrigatória**; sem ela a API não sobe. No `dotnet run` ela vem do `appsettings.Development.json`, que aponta para os bancos do compose em `localhost` (usuário/senha `sa`/`sa`). No compose, cada API tem seu próprio container Postgres, definido em `docker-compose.database.yml` (`catalog-db`, `orders-db`, `payment-db`, portas 5433–5435 no host, e `customers-db`, porta 5437) e recebe a connection string dele; as imagens usam o `Dockerfile` genérico da raiz (build args `PROJECT` e `ASSEMBLY`). Depois chama `EnsureCreatedAsync()` e popula dados (`Seed()` em `*.Infrastructure/Seeds`; no Catalog, os produtos vêm do `Seeds/products.json`, recurso embutido, com a marca de cada um no campo `Brand`, e a seed só roda com a tabela vazia, então trocar o arquivo ou mudar o modelo, como a coluna `Brand` e a extensão `unaccent` da busca, exige recriar o volume `catalog_data`: `docker compose stop catalog-api catalog-db && docker compose rm -f catalog-db && docker volume rm scorpornok-ecommerce_catalog_data`). Não há migrations do EF. Rodar uma API exige os bancos no ar (`docker compose -f docker-compose.database.yml up -d`).
- CORS: o `Gateway.Web.Api` (catálogo, cadastro e pedidos da loja vêm por ele; o `/graphql` dos subgraphs só o gateway chama), o `Catalog.Web.Api`, o `Orders.Web.Api`, o `Payments.Web.Api` (por causa do `POST /card-tokens`, que a loja não usa mais) e o `Customers.Web.Api` (sem `AllowCredentials`) liberam as origens de `Cors:AllowedOrigins` (`appsettings.json`, hoje `http://localhost:3000`), porque o front-end chama as APIs direto do navegador. No Orders a policy tem `AllowCredentials()` (exigido pelo SignalR) e a mesma lista vale para o handshake do WebSocket (`WebSocketOptions.AllowedOrigins`), já que o navegador não aplica CORS a ele.
- `POST /createOrder` (Orders) exige `Authorization: Bearer <access token do Keycloak>` e recebe `address { street, number, complement, district, city, state, zipCode }` (formato do cadastro, `OrderAddress`: complemento opcional, UF válida, CEP de 8 dígitos guardado só com dígitos e `Country` sempre `Brasil`; um `country` no corpo é ignorado), `customer { fullName, phone, cpf }` (`OrderBuyerMessage`: obrigatório, validado como no cadastro e **não** guardado no pedido; segue só no `OrderPlaced`), `items` (com `productId` numérico, o mesmo id do Catalog, e `units`) e `payment { cardToken, installments }` (`PaymentMethod`). Os erros do `400` são mensagens, como no resto do pedido (`UF inválida.`, `CPF inválido.`). As colunas `AddressNumber`, `AddressComplement` e `AddressDistrict` (tabela `OrderAddress`) exigem recriar o volume `orders_data`. O cartão nunca chega ao Orders: o checkout o tokeniza antes no `tokenizeCard` do Payments, pelo gateway. Sem `payment`, o pedido é registrado sem solicitar cobrança; com `payment` e sem token, `400` (`Informe o cartão.`); um `card` antigo no corpo é ignorado. Preço, nome e foto de cada item vêm do Catalog (porta `ICatalogProducts`, implementada pelo `HttpCatalogProducts` sobre o `GET /GetProductsByIds?ids=..` do Catalog, uma chamada por pedido, antes da transação, com limite de 5 s); `unitPrice`, `productName`, `pictureUrl` e `discount` do corpo são ignorados. A seção `Catalog:BaseAddress` é obrigatória (no `dotnet run`, `http://localhost:5064`; no compose, `http://catalog-api:8080`), e o registro do pedido depende do Catalog no ar: produto inexistente responde `400` (`Produto {id} não encontrado.`) e Catalog fora responde `503`, sem gravar nem cobrar. O cliente e o e-mail do pedido (para onde vai o resultado do pagamento) vêm dos claims `sub` e `email` do token; `userId` e `email` no corpo são ignorados. Responde `201` com `{ orderNumber, status, total }` (o `orderNumber` é `A` + 12 dígitos aleatórios do `RandomNumberGenerator`, gerado pelo `OrderNumber.New()` no construtor do `Order`, com índice único na coluna `Number`: uma colisão falha a gravação, desfaz a transação e não cobra nada), `400` com `{ errors }`, `401` sem token ou com token inválido/expirado, `403` com o e-mail não confirmado (`email_verified`) e `503` com o Catalog fora do ar. O pedido nasce `Pending`. A resposta `201` traz também `attempt` (1) e `maxAttempts` (`Order.MaxPaymentAttempts` = 3). **Nova tentativa de pagamento** (`allow-payment-retry`): `POST /orders/{orderNumber}/payment` (política `VerifiedCustomer`, corpo `{ cardToken, installments }` com um token novo do `POST /card-tokens`) leva o `RetryOrderPaymentCommand` ao `RetryOrderPaymentHandler`, que só aceita o dono, só pedido `Failed` e só até 3 tentativas, e, numa transação (outbox), chama `Order.RetryPayment(now)` — o pedido volta a `Pending`, `OrderPayment.Attempt` é incrementado, `AttemptRequestedAt` recebe a hora e o estado da consulta e do e-mail (`StatusCheckedAt`, `EmailSentAt`, `EmailAttempts`, `NextEmailAttemptAt`, `EmailFailedAt`, `EmailFailureReason`) é zerado, para a nova tentativa ter o seu prazo e o seu e-mail — e publica o `PaymentRequested` com o mesmo `Total` e o `Attempt`. Responde `202` com `{ orderNumber, status, attempt }`, `400` sem cartão, `404` para pedido inexistente ou de outro cliente (não revela o número, como o hub) e `409` se o pedido não está recusado ou as tentativas acabaram. Pedido `NotProcessed` não tem nova tentativa. Todas as mensagens do pagamento (`PaymentRequested`, `PaymentApproved`, `PaymentRejected`, `PaymentStatusRequested`, `PaymentStatusPending`, `PaymentNotProcessed`) levam `Attempt` (padrão 1, para mensagens antigas); o Payments usa a chave `{OrderNumber}-{Attempt}` (um pagamento por tentativa) e devolve a tentativa no resultado; `Order.ConfirmPayment`/`FailPayment`/`MarkPaymentNotProcessed` exigem a tentativa atual, então um resultado atrasado de tentativa anterior é ignorado; o prazo da consulta (`PendingOrderWatcher`) conta a partir de `Order.AttemptStartedAt` (`AttemptRequestedAt` ou a data do pedido); o hub manda `attempt` no `PaymentStatusChanged`, e o e-mail de recusa diz quantas tentativas restam ou que elas acabaram.
- **Histórico do cliente** (`add-order-history`): `GET /orders?page=1&pageSize=10` e `GET /orders/{orderNumber}` (o endereço do `Location` do `201`), ambos com a política `VerifiedCustomer` e o cliente do `sub`, levam o `GetCustomerOrdersQuery`/`GetCustomerOrderQuery` (`RequestAsync`) ao `CustomerOrdersHandler` (`Orders.CommandHandlers/.../History`). O `IOrderRepository` filtra pelo `CustomerId` na própria consulta (`GetCustomerOrdersAsync`/`GetCustomerOrderAsync`: `AsNoTracking`, `Include` dos itens, ordem `OrderDate` desc e `Id` desc). A lista responde `200 { items, page, pageSize, hasMore }`, com `pageSize` ajustado entre 1 e 50 (padrão 10) e `hasMore` vindo de uma linha a mais, sem `COUNT`; cada item tem `orderNumber`, `orderDate`, `status` (`OrderStatus.Name`), `total`, `itemCount` (soma das quantidades) e `pictureUrl` (do primeiro item). O detalhe traz `attempt`, `maxAttempts`, `canRetryPayment` (`Order.CanRetryPayment`), `address` sem país e `items` com `subtotal` = preço × quantidade; pedido de outro cliente ou inexistente → `404 { errors: ["Pedido não encontrado."] }`. Tudo vem do pedido gravado (nada do Catalog ou do Customers), e os DTOs não levam `PaymentId`, e-mail, cliente nem o estado do e-mail. O índice `(CustomerId, OrderDate)` só existe em banco novo (sem migrations); num `orders_data` antigo as consultas funcionam sem ele, e recriar o volume é opcional.
- **Autenticação no Orders** (seção `Keycloak`: `Authority`, o emissor público `http://localhost:8080/realms/scorponok`; `Audience`=`orders-api`; e, no compose, `MetadataAddress` em `keycloak:8080`): JwtBearer com `MapInboundClaims=false`, `ClockSkew` de 30 s e a política `VerifiedCustomer` (autenticado, `email_verified=true`, `sub` GUID e `email`) no endpoint e no hub. O `/health/ready` não depende do Keycloak.
- **Fluxo do pagamento** (MassTransit sobre RabbitMQ, configurado pela seção `RabbitMq` — `Host`, `Username`, `Password` —, no compose via `RabbitMq__Host: rabbitmq`): depois de salvar, o Orders publica `PaymentRequested` com o total do pedido e o `CardToken` (só o token; nada de número, validade ou CVV); o Payments consome, decide, grava e publica `PaymentApproved` ou `PaymentRejected`; o Orders consome, passa o pedido para `Confirmed` (com `PaymentId`) ou `Failed` e avisa o navegador pelo hub `/hubs/orders` (`WatchOrder(orderNumber)` → mensagem `PaymentStatusChanged { orderNumber, approved }`; quem acompanha um pedido já resolvido recebe o resultado na hora; a mensagem também leva `status` — `Confirmed`, `Failed` ou `NotProcessed` —, e `approved` continua por compatibilidade). O hub exige o token, que o navegador manda em `access_token` na query (o WebSocket não leva cabeçalho), e só o dono acompanha o pedido: para pedido de outro cliente ou inexistente, o `WatchOrder` lança `Order not found.` sem entrar no grupo. As filas (`payment-requested`, `payment-approved`, `payment-rejected`, e a `order-placed` do Customers) são duráveis: se um serviço estiver parado, a mensagem espera. Os consumidores do Orders, do Payments e do Customers usam a mesma retentativa (`UseTransientRetry`, em `Messaging/TransientRetry.cs` de cada `Infrastructure`): intervalos dobrando de 3 s até 2 min (3, 6, 12, 24, 48, 96 e 120 s, cerca de 5 minutos), com a mensagem sem confirmação no consumidor enquanto espera, de modo que um reinício da API a devolve à fila; `ArgumentException` (mensagem malformada) não é repetida. Esgotadas as tentativas, o MassTransit move a mensagem para `<fila>_error`, que ninguém reprocessa sozinho. Atenção: as APIs não sobem com o próprio banco fora (o `EnsureCreatedAsync` da partida falha) e o compose não as reinicia. Mas uma mensagem publicada antes de a fila existir é descartada, então o `payment-api` precisa ter subido ao menos uma vez. O `PaymentRequested` passa por um **outbox** (`AddEntityFrameworkOutbox<OrderContext>` com `UseBusOutbox`): o `OrderHandler` grava o pedido e a mensagem (tabela `OutboxMessage` do `orders-db`) na mesma transação, e um serviço em segundo plano do MassTransit a entrega ao RabbitMQ e apaga a linha depois da confirmação do broker. Assim o `POST /createOrder` responde `201` sem depender do broker; com o RabbitMQ fora (ou o `orders-api` reiniciado nesse meio-tempo), o pedido fica `Pending` e a mensagem sai quando o broker volta. O `PublishAsync` precisa vir antes do último `SaveChanges`, senão a mensagem não é gravada. Diagrama em `docs/diagrams/order-outbox.excalidraw`. Na mesma transação sai o `OrderPlaced` (todo pedido, com ou sem cartão: cliente, e-mail, comprador e endereço de entrega), consumido pelo `customers-api` na fila `order-placed`; com o Customers parado, a mensagem espera na fila, e o pedido não depende dele. O `orders-api` só sobe depois do `customers-api` no compose, porque uma mensagem publicada antes de a fila existir é descartada. CPF e telefone passam pelo outbox e pela fila, nunca pelo log. Nenhum dado de cartão passa pelo Orders, pelo outbox ou pelas filas: só o token. Trocar esse contrato num ambiente já no ar exige parar `orders-api` e `payment-api`, esvaziar `payment-requested` e `payment-requested_error`, recriar os volumes `orders_data` e `payment_data` e subir `payment-api`, `orders-api` e o `frontend` reconstruído, nessa ordem.
- **E-mail do resultado**: o consumidor só atualiza o status; quem envia o e-mail é o `OrderEmailDispatcher` (`BackgroundService` no `orders-api`), que a cada `Smtp:PollSeconds` (padrão 5 s) busca até 20 pedidos `Confirmed`/`Failed`/`NotProcessed` com `Payment.EmailSentAt` e `Payment.EmailFailedAt` nulos e `Payment.NextEmailAttemptAt` nulo ou vencido (os que nunca falharam primeiro), envia (texto simples, em português, com o total em reais) e marca um a um. O status do pedido nunca espera o e-mail, e um resultado repetido não gera outro e-mail (se o processo cair entre enviar e marcar, sai um segundo). O `SmtpOrderEmailSender` lança `EmailDeliveryException` com o tipo da falha (`SmtpOrderEmailSender.Classify`), e o dispatcher age por tipo: **`Recipient`** (endereço do pedido inválido, ou destinatário recusado com 5xx) → falha definitiva do pedido (`Order.MarkPaymentEmailFailed`: `EmailFailedAt` e `EmailFailureReason`), e a rodada segue; **`Message`** (4xx, mensagem recusada ou erro desconhecido) → conta tentativa (`EmailAttempts`) e agenda a próxima (`NextEmailAttemptAt` = `RetryBaseSeconds` × 2^(tentativa−1), até `RetryMaxSeconds`), com falha definitiva ao atingir `MaxEmailAttempts`; **`Server`** (conexão, TLS, autenticação, protocolo, remetente inválido ou recusado, servidor sem autenticação com usuário configurado) → encerra a rodada sem tocar nos pedidos e dobra a espera entre rodadas a partir de `PollSeconds`, até `RetryMaxSeconds`, voltando ao normal no primeiro envio bem-sucedido. Senha do SMTP errada é `Server`, para não levar todos os pedidos à falha definitiva por um erro de configuração. Falha definitiva gera `LogError` com o número do pedido; servidor fora gera um `LogWarning` só na primeira rodada e um `LogInformation` na volta. O `/health/email` (tag `email`, fora do `ready`) responde `503` quando a última rodada parou com o servidor fora (estado em memória no singleton `EmailDeliveryState`), `200` "Degraded" com `failedEmails` quando houve falha definitiva nas últimas 24 h, e `200` "Healthy" nos demais casos. Configuração na seção `Smtp` (`Host`, `Port`, `From`, `Username`, `Password`, `UseStartTls`, `PollSeconds`, `MaxEmailAttempts` (padrão 6), `RetryBaseSeconds` (60), `RetryMaxSeconds` (3600), validados como positivos na partida); no `dotnet run` aponta para o Mailpit em `localhost:1025`, no compose para `mailpit`. O Mailpit guarda as mensagens em memória (somem ao reiniciá-lo) e não entrega nada para fora.
- **Pedido preso em `Pending`** (`PendingOrderWatcher`, `BackgroundService` no `orders-api`, seção `PaymentCheck`: `TimeoutMinutes` 15, `IntervalSeconds` 60, `AlertAfterMinutes` 15; no compose, `PAYMENT_CHECK_*` no `.env`): a cada intervalo, busca pedidos `Pending` com `OrderDate` além do prazo e `Payment.StatusCheckedAt` nulo ou mais antigo que o intervalo (`Order.IsPaymentCheckDue`), publica `PaymentStatusRequested(OrderNumber, Attempt)` pelo outbox e grava `StatusCheckedAt` no mesmo `SaveChanges`. O Orders nunca decide sozinho: o `CheckPaymentStatusHandler` do Payments (consumidor `PaymentStatusRequestedConsumer`) busca pela chave `{OrderNumber}-{Attempt}`; com pagamento registrado republica `PaymentApproved`/`PaymentRejected` (o que também resgata um resultado parado em `payment-approved_error`), em processamento publica `PaymentStatusPending` (o Orders só registra no log e consulta de novo), e sem pagamento grava um `Payment` `Voided` (`Payment.Void`, mesma chave e mesmo índice único da cobrança) e publica `PaymentNotProcessed`. O Orders então passa o pedido para `NotProcessed` (código 11, "Pagamento não processado", `Order.MarkPaymentNotProcessed`, só sobre `Pending`), avisa a loja pelo hub e envia o e-mail "nada foi cobrado; refaça a compra". Uma solicitação que chegue depois da anulação encontra o `Voided` e é recusada (`PaymentRejected` com `Payment.VoidedReason`) sem passar pelo gateway; como o pedido já não está `Pending`, o Orders a ignora. Consulta e solicitação vêm de filas diferentes e podem ser processadas em qualquer ordem: com o Payments fora além do prazo, o pedido tende a terminar `NotProcessed` (nada cobrado), e a corrida entre as duas é decidida pelo índice único (a perdedora falha a gravação e a retentativa relê o registro).
- **Enviar e-mail de verdade** (ex.: Gmail, com verificação em 2 etapas e uma senha de app): só configuração, sem mudar código. No `dotnet run`, use o user-secrets do `Orders.Web.Api` (`dotnet user-secrets set "Smtp:Password" "<senha de app>" --project src/backend/Store/Orders.Web.Api`, e o mesmo para `Smtp:Host`=`smtp.gmail.com`, `Smtp:Port`=`587`, `Smtp:UseStartTls`=`true`, `Smtp:Username` e `Smtp:From`=seu e-mail). No compose, crie um `.env` na raiz (ignorado pelo git) com `SMTP_HOST`, `SMTP_PORT`, `SMTP_FROM`, `SMTP_USERNAME`, `SMTP_PASSWORD` e `SMTP_USE_STARTTLS=true`; sem ele, valem os padrões do Mailpit. O mesmo `.env` vale para os e-mails do Keycloak (confirmação de cadastro): o `smtpServer` do realm usa placeholders (`${SMTP_HOST:mailpit}` etc.) que o `docker-compose.identity.yml` preenche com as `SMTP_*`, e a autenticação SMTP só é ligada quando há `SMTP_USERNAME`. Esses valores só entram na importação do realm, então depois de mudar o `.env` é preciso recriar o volume `keycloak_data` (apaga as contas) ou ajustar em *Realm settings* → *Email* no console. Nunca coloque a senha em um `appsettings*.json` ou no `scorponok-realm.json` versionados.
- **Identidade (Keycloak)**: `docker-compose.identity.yml` sobe o `keycloak` (26.7, `start-dev`, porta 8080; console de administração em http://localhost:8080 com `admin`/`admin`, trocáveis por `KEYCLOAK_ADMIN_USERNAME`/`KEYCLOAK_ADMIN_PASSWORD` num `.env`) e o `keycloak-db` (Postgres 16, porta 5436). O realm `scorponok` vem de `keycloak/scorponok-realm.json`, importado na partida só se ainda não existir: cadastro só com o e-mail, link de confirmação pelo Mailpit e definição da senha (mínimo 8) depois de abrir o link; client público `scorponok-web` (PKCE, origem `http://localhost:3000`) com os audiences `orders-api`, `customers-api` e `gateway-api` nos tokens (mappers `orders-api-audience`, `customers-api-audience` e `gateway-api-audience`; num realm já importado, os dois últimos podem ser adicionados pelo console, em *Clients* → `scorponok-web` → *Client scopes*, ou pelo `kcadm.sh` do container, sem recriar o volume). A loja mostra o login e o cadastro num modal (iframe), por isso o realm libera o iframe só para a loja (`browserSecurityHeaders`: `frame-ancestors 'self' http://localhost:3000`, sem `X-Frame-Options`); outra origem da loja precisa entrar ali também. As telas estão em pt-BR (único idioma do realm, também nos e-mails do Keycloak) e usam o tema `scorponok` (`keycloak/themes/scorponok/login`, montado em `/opt/keycloak/themes`): herda o `keycloak.v2` e só troca cores, fonte e marca no `scorponok.css`, e alguns textos em `messages_pt_BR.properties`, e o `js/embedded.js` deixa a página compacta dentro do modal e manda a altura dela para a loja; o `start-dev` não guarda o tema em cache, então mudanças aparecem ao recarregar (só o `loginTheme` e o idioma, no realm, exigem reimportar). Para aplicar uma mudança no arquivo, recrie o volume: `docker compose stop keycloak keycloak-db && docker compose rm -f keycloak keycloak-db && docker volume rm scorpornok-ecommerce_keycloak_data`. O emissor dos tokens é sempre `http://localhost:8080/realms/scorponok`; os containers buscam as chaves em `keycloak:8080` (`KC_HOSTNAME` + `KC_HOSTNAME_BACKCHANNEL_DYNAMIC`). O healthcheck usa a porta de gerenciamento 9000.
- Como não há migrations, mudanças no modelo do EF não alteram um banco já criado. - Health checks: `/health/live` (só o processo, sem checks), `/health/email` (só no Orders: envio do e-mail do resultado, descrito acima) e `/health/ready` (checks com a tag `ready`: o `AddDbContextCheck` do banco em Catalog, Orders, Payments e Customers). O Customers, como o Orders, tira o bus do `ready` e o expõe em `/health/bus`. O MassTransit registra o check do bus com a tag `ready`; no Orders ele é trocado para a tag `bus` (`ConfigureHealthCheckOptions` no `AddInfrastructure`), então o `ready` do Orders só depende do banco, porque o `POST /createOrder` funciona sem o broker graças ao outbox, e o estado do broker fica em `/health/bus` (`200` com o broker no ar, `503` sem ele). O bus fica `Degraded` quando o broker cai com a API no ar e `Unhealthy` quando ela sobe sem o broker; o `/health/bus` responde `503` nos dois casos. No Payments o check do bus continua no `ready`, com o mapeamento padrão: `200` (`Degraded`) se o broker cair depois da partida, `503` se ele subir sem o broker. O Orders e o Payments também expõem `/health/ops` (tag `ops`, fora do `ready`): o `ErrorQueuesHealthCheck` (em `Monitoring/` de cada `Infrastructure`) consulta a API de gerenciamento do RabbitMQ (`RabbitMq:ManagementUrl`, `localhost:15672` no `dotnet run`, `rabbitmq:15672` no compose, com as credenciais da seção `RabbitMq`) e fica `Unhealthy` (`503`) com mensagens nas filas `_error` que a API consome (nomes do `KebabCaseEndpointNameFormatter`; fila inexistente conta como vazia; API de gerenciamento fora → `Degraded`, `200`); no Orders, o `StuckOrdersHealthCheck` fica `Unhealthy` com pedidos `Pending` além de `TimeoutMinutes + AlertAfterMinutes`. Para reprocessar, mova as mensagens da fila `_error` de volta à fila de origem pelo painel do RabbitMQ (é seguro: o Payments não cobra de novo, o Orders ignora resultado de pedido com desfecho e o Customers ignora pedido já registrado).
- `Program` é declarado como `public partial class Program` para que os testes possam usar `WebApplicationFactory<Program>`.
