# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Visão geral

Scorponok é um backend de e-commerce modular em .NET, feito para estudo e demonstração (DDD, CQRS, MediatR, domain notifications, event sourcing). O README ainda descreve o .NET Core 3.1. O código já migrou para **net8.0** (`Programming.Functional*` ainda é net6.0). Comentários no código, o `use-case.md` e parte da documentação estão em português.

## Comandos

```bash
dotnet build Scorponok.sln                     # compila tudo (CI: restore → build → test no master)
dotnet test Scorponok.sln                      # roda todos os testes
dotnet test src/backend/Frameworker/Programming.Functional.Tests   # um projeto de teste
dotnet test src/backend/Frameworker/Programming.Functional.Tests --filter "FullyQualifiedName~OptionTests"  # uma classe/teste
dotnet run --project src/backend/Catalog/Catalog.Web.Api           # sobe a API de Catalog (precisa dos bancos do compose)
dotnet run --project src/backend/Store/Orders.Web.Api              # sobe a API de Orders (precisa dos bancos, do RabbitMQ e do Mailpit do compose)
dotnet run --project src/backend/Payments/Gateway.Payment.Web.Api   # sobe a API de Payments (precisa dos bancos e do RabbitMQ do compose)
docker compose up -d --build                   # Catalog (5064), Orders (5224) e Payment (5220), cada um com seu Postgres 16, o RabbitMQ, o Mailpit e o front-end (3000); Swagger em /swagger
docker compose -f docker-compose.database.yml up -d   # só os bancos (o docker-compose.yml raiz inclui este arquivo)
docker compose -f docker-compose.messaging.yml up -d  # só o RabbitMQ (5672; painel em http://localhost:15672, guest/guest)
docker compose -f docker-compose.mail.yml up -d       # só o Mailpit (SMTP 1025; caixa de entrada em http://localhost:8025)
docker compose -f docker-compose.frontend.yml up -d --build   # só o front-end (também incluído pelo docker-compose.yml)
```

- `Programming.Functional.Tests` é net6.0, então rodá-lo exige o runtime do .NET 6 (ou trocar o target).
- Cada projeto `*.Web.Api` tem um arquivo `.http` para testar os endpoints.

## Versões de pacotes

Todas as versões de pacotes são propriedades MSBuild no `Directory.Build.props`, por exemplo `Version="$(MediatRNet8)"`. Adicione ou atualize versões lá, não direto no csproj. Os projetos usam `<TargetFramework>$(TargetFrameworkNet8)</TargetFramework>`. O arquivo de props define versões legadas (EF Core 3.1.x, MediatR 7) e versões net8 (`*Net8`), e os projetos misturam as duas. Por exemplo, projetos net8 ainda referenciam o EF Core `$(EntityFrameworkCore)` = 3.1.19. Os projetos Web API fixam algumas versões direto no csproj (Swashbuckle, OpenApi).

## Arquitetura

Os bounded contexts ficam em `src/backend/` (`src/frontend/` contém o front-end React + Vite, com seu próprio `CLAUDE.md`). Cada um é dividido em projetos por camada, e as dependências apontam para dentro, até o Domain:

- **Catalog** (lado de leitura / queries): `Catalog.Domain` (entidade `Product`) ← `Catalog.Queries` (`IProductQueries`, `IApplicationCatalogDbContext`, paginação via `ToPagedList`/`IPagedList` do `Frameworker.EntityFrameworkCore`) ← `Catalog.Infrastructure` (`ApplicationCatalogDbContext`, configurações do EF, `AddInfrastructure`) ← `Catalog.Web.Api`.
- **Store / Orders** (lado de escrita / commands): `Orders.Domain` (agregado `Order` com `ConfirmPayment`/`FailPayment`, que só agem sobre pedido `Pending`, e `Email`/`PaymentEmailSentAt`/`MarkPaymentEmailSent` para o e-mail do resultado; validadores FluentValidation; `IOrderRepository` com `GetByNumberAsync` e `GetAwaitingPaymentEmailAsync`) ← `Orders.CommandHandlers` (`IRequestHandler`s do MediatR: o `OrderHandler` monta um `Order` com o `OrderBuilder` fluente, valida com `IsValid()`, salva e publica `PaymentRequested`; `OrderPaymentHandlers` aplica o resultado do pagamento e chama o `IOrderPaymentNotifier`; `IOrderEmailSender` e o texto do e-mail em `OrderPaymentEmail`) ← `Orders.Infrastructure` (`OrderContext`, repositório, consumidores `PaymentApproved`/`PaymentRejectedConsumer`, MassTransit, e-mail em `Email/` — `SmtpOrderEmailSender` com MailKit e o `OrderEmailDispatcher` — e DI em `AddInfrastructure`) ← `Orders.Web.Api` (endpoints e o hub SignalR `OrderHub`). O Orders não tem código de pagamento; o `Order` guarda só o `PaymentId`.
- **Payments**: `Gateway.Payment.Domain` (agregado `Payment`, que guarda só os 4 últimos dígitos do cartão e nunca o CVV; `IPaymentGateway`, `PaymentRequest`/`PaymentResult`, `IPaymentRepository`) ← `Gateway.Payment.CommandHandlers` (`ProcessPaymentCommand` e handler: cobra no gateway, grava e publica `PaymentApproved`/`PaymentRejected`; se o pedido já tem pagamento, só republica o resultado) ← `Gateway.Payment.Data` (`PaymentContext` no schema `payment`, índice único em `OrderNumber`; `PaymentRepository`; `PaymentGateway` stub, que recusa cartão terminado em `0000`; consumidor `PaymentRequestedConsumer`; MassTransit e DI em `AddInfrastructure`; e o event store antigo, `EventStoreContext`/`SqlEventStore`, sem uso) ← `Gateway.Payment.Web.Api` (sem endpoints de negócio: só consome mensagens).
- **Shared/Shared.Code**: os blocos básicos de DDD/CQRS. São eles `Entity<T>` (acumula erros de validação), `ValueObject`, `IAggregateRoot`, `IRepository`/`IUnitOfWork`, `Message`/`CommandBase`/`Event`, a base `CommandHandler` e `DomainNotification` com seu handler. Também tem `IMemoryBus`/`MemoryBus`, um wrapper fino sobre o `IMediator`: `SendAsync` para commands sem retorno (`Message`) e `RequestAsync` para commands com resposta (`Message<TResponse>`). O `RaiseEvent` está comentado (não faz nada). Em `IntegrationEvents/` ficam os contratos trocados entre contextos pelo RabbitMQ (`PaymentRequested`, `PaymentApproved`, `PaymentRejected`) e o `IIntegrationEventPublisher`, que os handlers usam para publicar sem depender do MassTransit.
- **Frameworker**: infraestrutura reutilizável. `Programming.Functional` fornece `Result`/`Result<T>`/`Maybe<T>`/`Option<T>`. `Frameworker.EntityFrameworkCore` fornece paginação. `Frameworker.Integration.Tests` fornece bases de `WebApplicationFactory` com Testcontainers (Postgres/Oracle/Sqlite), que escolhem o `appsettings.<dbtype>.json`.

### Convenções das Web APIs

- Minimal APIs: os endpoints são métodos de extensão de `WebApplication` em `WebApplicationExtensions/` (ex.: `app.GetAllProducts()`, `app.CreateOrder()`), chamados no `Program.cs`.
- Os commands chegam aos handlers assim: endpoint ou consumidor do MassTransit → `IMemoryBus.SendAsync(command)` (ou `RequestAsync`, quando o handler devolve um resultado) → MediatR → handler. Os handlers são registrados explicitamente em cada `Infrastructure/Extensions/ServiceCollectionExtensions.cs`, junto com o scan do assembly.
- **A connection string (`ConnectionStrings:ConnectionString`) é obrigatória**; sem ela a API não sobe. No `dotnet run` ela vem do `appsettings.Development.json`, que aponta para os bancos do compose em `localhost` (usuário/senha `sa`/`sa`). No compose, cada API tem seu próprio container Postgres, definido em `docker-compose.database.yml` (`catalog-db`, `orders-db`, `payment-db`, portas 5433–5435 no host) e recebe a connection string dele; as imagens usam o `Dockerfile` genérico da raiz (build args `PROJECT` e `ASSEMBLY`). Depois chama `EnsureCreatedAsync()` e popula dados (`Seed()` em `*.Infrastructure/Seeds`). Não há migrations do EF. Rodar uma API exige os bancos no ar (`docker compose -f docker-compose.database.yml up -d`).
- CORS: o `Catalog.Web.Api` e o `Orders.Web.Api` liberam as origens de `Cors:AllowedOrigins` (`appsettings.json`, hoje `http://localhost:3000`), porque o front-end chama as APIs direto do navegador. No Orders a policy tem `AllowCredentials()` (exigido pelo SignalR) e a mesma lista vale para o handshake do WebSocket (`WebSocketOptions.AllowedOrigins`), já que o navegador não aplica CORS a ele.
- `POST /createOrder` (Orders) recebe `userId`, `email` (obrigatório, para onde vai o resultado do pagamento), `address`, `items` (com `productId` numérico, o mesmo id do Catalog) e `card`. Responde `201` com `{ orderNumber, status, total }` ou `400` com `{ errors }`. O pedido nasce `Pending`.
- **Fluxo do pagamento** (MassTransit sobre RabbitMQ, configurado pela seção `RabbitMq` — `Host`, `Username`, `Password` —, no compose via `RabbitMq__Host: rabbitmq`): depois de salvar, o Orders publica `PaymentRequested` com o total do pedido (o `card.amount` do cliente é ignorado) e o `card`; o Payments consome, decide, grava e publica `PaymentApproved` ou `PaymentRejected`; o Orders consome, passa o pedido para `Confirmed` (com `PaymentId`) ou `Failed` e avisa o navegador pelo hub `/hubs/orders` (`WatchOrder(orderNumber)` → mensagem `PaymentStatusChanged { orderNumber, approved }`; quem acompanha um pedido já resolvido recebe o resultado na hora). As filas (`payment-requested`, `payment-approved`, `payment-rejected`) são duráveis: se um serviço estiver parado, a mensagem espera. Mas uma mensagem publicada antes de a fila existir é descartada, então o `payment-api` precisa ter subido ao menos uma vez. O `PaymentRequested` passa por um **outbox** (`AddEntityFrameworkOutbox<OrderContext>` com `UseBusOutbox`): o `OrderHandler` grava o pedido e a mensagem (tabela `OutboxMessage` do `orders-db`) na mesma transação, e um serviço em segundo plano do MassTransit a entrega ao RabbitMQ e apaga a linha depois da confirmação do broker. Assim o `POST /createOrder` responde `201` sem depender do broker; com o RabbitMQ fora (ou o `orders-api` reiniciado nesse meio-tempo), o pedido fica `Pending` e a mensagem sai quando o broker volta. O `PublishAsync` precisa vir antes do último `SaveChanges`, senão a mensagem não é gravada. Diagrama em `docs/diagrams/order-outbox.excalidraw`. Os dados do cartão, inclusive o CVV, trafegam na fila e ficam no `orders-db` (na `OutboxMessage`) até a entrega.
- **E-mail do resultado**: o consumidor só atualiza o status; quem envia o e-mail é o `OrderEmailDispatcher` (`BackgroundService` no `orders-api`), que a cada `Smtp:PollSeconds` (padrão 5 s) busca até 20 pedidos `Confirmed`/`Failed` com `PaymentEmailSentAt` nulo, envia (texto simples, em inglês) e marca um a um. Com o SMTP fora, o status não espera e o e-mail sai numa rodada seguinte; um resultado repetido não gera outro e-mail (se o processo cair entre enviar e marcar, sai um segundo). Configuração na seção `Smtp` (`Host`, `Port`, `From`, `Username`, `Password`, `UseStartTls`, `PollSeconds`); no `dotnet run` aponta para o Mailpit em `localhost:1025`, no compose para `mailpit`. O Mailpit guarda as mensagens em memória (somem ao reiniciá-lo) e não entrega nada para fora.
- **Enviar e-mail de verdade** (ex.: Gmail, com verificação em 2 etapas e uma senha de app): só configuração, sem mudar código. No `dotnet run`, use o user-secrets do `Orders.Web.Api` (`dotnet user-secrets set "Smtp:Password" "<senha de app>" --project src/backend/Store/Orders.Web.Api`, e o mesmo para `Smtp:Host`=`smtp.gmail.com`, `Smtp:Port`=`587`, `Smtp:UseStartTls`=`true`, `Smtp:Username` e `Smtp:From`=seu e-mail). No compose, crie um `.env` na raiz (ignorado pelo git) com `SMTP_HOST`, `SMTP_PORT`, `SMTP_FROM`, `SMTP_USERNAME`, `SMTP_PASSWORD` e `SMTP_USE_STARTTLS=true`; sem ele, valem os padrões do Mailpit. Nunca coloque a senha em um `appsettings*.json` versionado.
- Como não há migrations, mudanças no modelo do EF não alteram um banco já criado. Recrie o volume do banco do contexto afetado (ex.: `docker compose stop orders-api orders-db && docker compose rm -f orders-db && docker volume rm scorpornok-ecommerce_orders_data`).
- Health checks: `/health/live` (só o processo, sem checks) e `/health/ready` (checks com a tag `ready`: o `AddDbContextCheck` do banco em Catalog, Orders e Payments e, em Orders e Payments, o check do bus que o MassTransit registra com a tag `ready`). Sem o broker, o `/health/ready` do Orders responde `503`, embora o `POST /createOrder` continue funcionando pelo outbox.
- `Program` é declarado como `public partial class Program` para que os testes possam usar `WebApplicationFactory<Program>`.

## Testes

- `src/backend/Tests/Ecommerce.Scenarios.Integration.Spec.Tests`: testes BDD com SpecFlow + NUnit contra o `Catalog.Web.Api` via `WebApplicationFactory<Program>` (`Hooks/Hook.cs`). O `Features/*.feature.cs` é gerado no build, então edite o arquivo `.feature`.
- `src/backend/Frameworker/Programming.Functional.Tests`: testes unitários com NUnit + FluentAssertions + Moq.
- `src/backend/Store/Orders.Tests`: testes unitários do Orders (validação e transições do `Order`, handlers com repositório e publicador mockados, consumidores no test harness do MassTransit, `MemoryBus.RequestAsync`, texto do e-mail, opções de SMTP e o `OrderEmailDispatcher` com repositório e sender mockados), com NUnit + FluentAssertions + Moq. Rode com `dotnet test src/backend/Store/Orders.Tests`.
- `src/backend/Payments/Gateway.Payment.Tests`: testes do Payments (`Payment`, regra do gateway, `ProcessPaymentHandler`, consumidor no test harness). Rode com `dotnet test src/backend/Payments/Gateway.Payment.Tests`.
- `src/backend/Tests/Ecommerce.Integration.Tests` **não está na solution** e está desatualizado. É netcoreapp3.1 e referencia projetos que não existem mais (`Store.Web.Api`, `Frameworker.Scorponok.*`).
- `Snippets/` contém snippets do Visual Studio com o layout dos testes unitários.
