# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Visão geral

Front-end da loja Scorponok, feito em React 19 + Vite (SPA, sem servidor Node em produção), TypeScript, React Router 7, Tailwind CSS v4 e componentes shadcn/ui. Ele parte do template **BloomShop** (ThemeWagon), que era em Next.js, por isso o `package.json` ainda se chama `bloom-ecommerce-template` e a marca ainda é BloomShop. Os textos da UI estão em português (pt-BR), e os preços são formatados em reais pelo `formatPrice` de `src/lib/utils.ts` (`R$ 1.299,99`). O backend .NET fica em `../backend` (veja o `CLAUDE.md` da raiz do repositório). Os produtos vêm do `Catalog.Web.Api` pelo gateway GraphQL (`Gateway.Web.Api`), que precisam estar no ar: sem eles, a home e as páginas de produto mostram o `ErrorState`.

## Comandos

```bash
npm install
npm run dev      # servidor de desenvolvimento em http://localhost:3000
npm run build    # checagem de tipos (tsc) + build de produção em dist/
npm run preview  # serve o dist/ em http://localhost:3000
npm run lint     # lint (eslint .)
```

As URLs das APIs vêm de `VITE_GRAPHQL_URL` (padrão `http://localhost:5200/graphql`, o gateway GraphQL, por onde vêm o catálogo, o cadastro do cliente e os pedidos), `VITE_ORDERS_API_URL` (padrão `http://localhost:5224`, só o hub SignalR do pagamento) e `VITE_PAYMENTS_API_URL` (padrão `http://localhost:5220`, a tokenização do cartão), as portas do `dotnet run` e do compose, e a do Keycloak de `VITE_KEYCLOAK_URL` (padrão `http://localhost:8080`). Elas são embutidas no JavaScript durante o build e usadas pelo navegador, então precisam ser endereços que o browser alcance (nunca o nome de um container). No Docker, o serviço `frontend` fica em `docker-compose.frontend.yml` na raiz do repositório (incluído pelo `docker-compose.yml`) e sobe em http://localhost:3000. A imagem vem do `Dockerfile` desta pasta: faz o build com Node e serve o `dist/` com nginx (`nginx.conf`, com fallback para `index.html` por ser SPA; `/assets/`, com hash no nome, fica 1 ano em cache, e as fotos de `/catalog-imgs/` ficam 30 dias, revalidadas depois pelo ETag, com 404 para imagem inexistente). Para mudar as URLs no Docker, use os build args `VITE_GRAPHQL_URL`, `VITE_ORDERS_API_URL`, `VITE_PAYMENTS_API_URL` e `VITE_KEYCLOAK_URL` (definidos no `docker-compose.frontend.yml`).

- O dev server e o container usam a porta 3000 porque `http://localhost:3000` é a origem liberada no CORS do `Gateway.Web.Api`, do `Orders.Web.Api` e do `Payments.Web.Api` (`Cors:AllowedOrigins` no `appsettings.json` de cada um) e no client `scorponok-web` do Keycloak (redirect, web origin e logout em `keycloak/scorponok-realm.json` na raiz). Outra porta ou origem precisa ser adicionada nos quatro.
- Não há testes nem framework de testes configurado.

## Arquitetura

- **Entrada**: `index.html` (título, meta e fonte Inter via Google Fonts) carrega `src/main.tsx`, que monta `<BrowserRouter>` e `src/App.tsx`. O `App` tem o layout (`AuthProvider`, `CartProvider`, `Header`, `Footer`) e as rotas.
- **Autenticação**: login e cadastro pelo formulário do Keycloak (realm `scorponok`, client público `scorponok-web`, Authorization Code + PKCE), com `oidc-client-ts`, num modal da loja (`src/components/AuthModal.tsx`, a página do Keycloak num iframe), sem sair da página. `src/lib/auth.ts` cria o `userManager` (escopo `openid email`, sessão no `localStorage` na chave `oidc.user:http://localhost:8080/realms/scorponok:scorponok-web`, renovação silenciosa pelo refresh token). `src/context/AuthContext.tsx` tem o `AuthProvider` (que renderiza o modal) e o `useAuth()`: `user`, `loading`, `email`, `login()` e `register()` (abrem o modal no login ou direto no cadastro, com `prompt=create`), `expireSession()` (descarta a sessão local recusada pela API e abre o login), `logout()` e `getAccessToken()` (renova o token vencido; nulo sem sessão). A URL do iframe vem de `createModalSigninUrl` (`lib/auth.ts`, um `OidcClient` com as mesmas configurações e o mesmo state no `localStorage`). O Keycloak volta para `public/auth/modal-callback.html`: no iframe, a página manda a URL com o code ao `AuthProvider` (`postMessage`), que conclui com `signinRedirectCallback(url)` e fecha o modal; numa aba própria (o link de confirmação do e-mail), ela segue para `/auth/callback` (`AuthCallbackPage`), que conclui e navega para o `returnTo` guardado no `state` (a página em que o modal foi aberto). Um login concluído em outra aba chega pelo evento `storage` e também fecha o modal. O tema do Keycloak manda a altura da página (`scorponok:kc-height`) para o modal ajustar o iframe; o `AuthModal` só aceita essa mensagem da origem do Keycloak e fecha com Esc, o X ou um clique fora. O `RequireAuth` (`src/components/RequireAuth.tsx`) mostra o conteúdo só com sessão e, sem ela, abre o login no modal; se o cliente o fechar, mostra "Entre para continuar" (com o texto do `message`, que cada página escolhe) com "Entrar" e "Cadastrar-se". O `Header` mostra "Entrar"/"Cadastrar-se" sem sessão e, com sessão, o e-mail como menu da conta (`layout/AccountMenu.tsx` no desktop; no menu móvel, os mesmos itens) com "Meu cadastro", "Meus pedidos" e "Sair". No cadastro, o Keycloak pede só o e-mail; a senha é definida depois de abrir o link de confirmação (no Mailpit, em dev).
- **Dados**: `src/lib/graphql.ts` é o cliente mínimo do gateway GraphQL (`graphqlRequest(query, variables, signal | { signal, accessToken })`: `POST` em `VITE_GRAPHQL_URL`, com `Authorization: Bearer` quando há token; `401` ou `AUTH_NOT_AUTHENTICATED` viram `SessionExpiredError` (`lib/session.ts`, reexportado por `lib/orders.ts`); lança erro com status diferente de 200 ou com `errors` na resposta, como quando o Catalog está fora). `src/lib/catalog.ts` usa esse cliente: `getProducts(page, pageSize, signal)` → `products(page, pageSize)` (as regras do `GET /Products` do Catalog, no máximo 20 por página, com o mesmo `pageInfo`) e `getProduct(id, signal)` → `productById(id)` (`null` quando não existe). Ele converte `pictureUri` em `image`. As chamadas saem do navegador e aparecem na aba Network como `POST /graphql`; o navegador não chama o Catalog direto. Os componentes as fazem via `useRequest(key, load)` (`src/hooks/useRequest.ts`), que devolve `loading`/`data`/`error`/`retry`, refaz a chamada quando `key` muda e cancela a anterior com `AbortController`. Em dev, o `StrictMode` monta tudo duas vezes, então a primeira chamada aparece como cancelada no Network. Os produtos vêm do seed do backend (281 tênis da Netshoes em `Catalog.Infrastructure/Seeds/products.json`, lido pelo `CatalogDbContextSeed.cs`). O `pictureUri` é um caminho relativo (`/catalog-imgs/<Sku>.jpg`), servido pela própria loja a partir de `public/catalog-imgs`, e usado direto em `<img>`. `src/lib/orders.ts` é o cliente dos pedidos pelo gateway (subgraph do Orders): `createOrder(request, accessToken)` → `placeOrder` (vão só `productId` e `units` dos itens; preço, nome e foto vêm do Catalog) e devolve `{ ok: true, order }` ou `{ ok: false, errors }` com as mensagens de `VALIDATION`; `CATALOG_UNAVAILABLE`, falha de rede e outros erros viram exceção. A entrada não leva cliente nem e-mail (o Orders os lê do token do Keycloak) nem o cartão: leva `payment { cardToken, installments }`. Para o histórico, `getMyOrders(page, accessToken, signal)` (`myOrders`, `ORDERS_PAGE_SIZE`; devolve `{ items, page, pageSize, hasMore }`) e `getMyOrder(orderNumber, accessToken, signal)` (`myOrder`; `null` para pedido inexistente e de outro cliente). Sem sessão válida, `SessionExpiredError`. O `ORDERS_API_URL` (`VITE_ORDERS_API_URL`) fica só para o hub do pagamento. A API devolve o `status` com o nome do enum, e `src/lib/orderStatus.ts` traduz (`orderStatusView`: "Aguardando pagamento", "Pago", "Pagamento recusado", "Pagamento não processado", com a cor do selo `OrderStatusBadge`) e formata a data (`formatOrderDate`). `src/lib/payments.ts` é o cliente do `Payments.Web.Api`: `tokenizeCard(payment)` faz `POST /card-tokens` com o cartão e devolve `{ ok: true, token }` no 201 ou `{ ok: false, errors }` (por campo do formulário) no 400; falha de rede e outros status viram exceção. O `CheckoutPage` tokeniza depois de conferir a sessão e antes do `createOrder`: erro de campo marca o campo, falha do serviço mostra "Não foi possível validar o cartão agora…" sem criar o pedido, e o token não é guardado nem reaproveitado. `src/lib/customers.ts` é o cliente do cadastro pelo gateway (subgraph do Customers): `getProfile(accessToken, signal)` (`me`; sem cadastro, só o e-mail e o resto `null`) e `saveProfile(profile, accessToken)` (`updateMyProfile`, `{ ok: true, profile }` com o cadastro salvo ou `{ ok: false, errors }` com os erros por campo, nas chaves de sempre, como `cpf` e `address.zipCode`); sem sessão válida, `SessionExpiredError`. A API devolve telefone, CPF e CEP só com dígitos, e a loja formata. `src/lib/brazil.ts` tem as regras do cadastro, iguais às do backend (CPF com dígitos verificadores, telefone com DDD, UF da lista `BRAZILIAN_STATES`, CEP de 8 dígitos, nome e sobrenome) e as máscaras (`formatCpf`, `formatPhone`, `formatZipCode`). `src/lib/orderHub.ts` conecta ao hub SignalR `/hubs/orders` do Orders (pacote `@microsoft/signalr`) com o token (`accessTokenFactory`; o SignalR o manda em `access_token` na query do WebSocket): `watchOrderPayment(orderNumber, getAccessToken, signal, attempt = 1)` (ignora o desfecho de tentativa anterior a `attempt`) chama `WatchOrder` e resolve com o desfecho (`PaymentOutcome`: `"approved"`, `"declined"` ou `"notProcessed"`, pelo campo `status` da mensagem, com `approved` como fallback) quando chega a mensagem `PaymentStatusChanged` daquele pedido. Se o pedido já estiver resolvido, a mensagem chega na hora. A função rejeita quando o `signal` é abortado ou a conexão falha, e sempre encerra a conexão. Não há consulta periódica do pedido.
- **Carrinho**: `src/context/CartContext.tsx` lê e grava o carrinho no `localStorage` (chave `cart`) via `useSyncExternalStore`. O `CartProvider` envolve toda a aplicação em `src/App.tsx`, e os componentes o acessam com `useCart()`. O `addToCart` sempre soma 1 à quantidade, então a página de produto chama a função em loop para adicionar N unidades.
- **Rotas** (`src/App.tsx`, páginas em `src/pages/`): `/` (`HomePage`, lista paginada com 18 produtos por página; a página atual fica na query string `?page=N`, lida em `ProductList` e navegada pelo `ProductPagination`), `/product/:productId` (`ProductPage`), `/cart`, `/checkout` (`CheckoutPage`, exige login), `/account/profile` (`ProfilePage`, "Meu cadastro", exige login), `/account/orders` (`OrdersPage`, "Meus pedidos", exige login), `/account/orders/:orderNumber` (`OrderDetailPage`, exige login), `/contact`, `/auth/callback` (`AuthCallbackPage`) e `*` (`NotFoundPage`). O `public/auth/modal-callback.html` é estático, fora do React. Use `Link`/`useNavigate`/`useLocation` de `react-router`.
- **Checkout**: a `CheckoutPage` redireciona para `/cart` se o carrinho estiver vazio e, só depois, exige login (`RequireAuth`), para não mandar ao Keycloak quem seria devolvido ao carrinho. Ela guarda o formulário em `useState`. Os blocos ficam em `src/components/checkout/` (`CheckoutItems`, `AccountEmail` (o e-mail da conta, só leitura: é para ele que o Orders envia o resultado), `BuyerForm` (nome, telefone e CPF, com máscara), `ShippingAddressForm` (endereço no formato do cadastro: CEP, rua, número, complemento opcional, bairro, cidade e UF numa lista; sem país, a entrega é só no Brasil), `PaymentForm`, `CheckoutSummary`, `OrderConfirmation`). `BuyerForm` e `ShippingAddressForm` também são usados na `ProfilePage`. A validação é a função pura `validateCheckout(buyer, address, payment)` em `src/lib/checkout.ts` (`validateBuyer` e `validateAddress` seguem as regras de `lib/brazil.ts`), que roda antes do envio; o corpo do `createOrder` leva `customer` (o comprador) e `address`. Com sessão, a página busca o cadastro (`getProfile`) e preenche comprador e endereço só nos campos ainda vazios (`fillEmpty`); o que o cliente muda ali vale só para o pedido. Sem cadastro, ou com o Customers fora, os campos ficam em branco e o checkout segue normal. Ao confirmar, a página pede o token ao `getAccessToken()`; sem sessão, ou com `401` do Orders, chama `expireSession()`, sem registrar o pedido: o login abre no modal sobre o checkout, e carrinho e formulário continuam preenchidos para confirmar de novo. No sucesso, a página mostra a `OrderConfirmation` com o número do pedido, sem esvaziar o carrinho; no erro, mantém carrinho e formulário. A `OrderConfirmation` recebe o pedido e o e-mail da conta, começa em "Processando" e espera o resultado do pagamento pelo hub (`watchOrderPayment`, com a tentativa acompanhada: mensagens de tentativa anterior são ignoradas), mostrando "Aprovado" ("Obrigado pela sua compra!"), "Recusado" ou "Não processado" (o Orders deu o pedido como não processado depois do prazo: nada foi cobrado e o cliente pode refazer a compra). O carrinho só é esvaziado (`clearCart()`, uma vez) quando o pagamento fica "Aprovado" ou "Pendente"; na recusa ele continua. Em "Recusado", enquanto `attempt < maxAttempts` (da resposta do `createOrder`), a tela mostra o `RetryPaymentForm` (`components/orders/RetryPaymentForm.tsx`, compartilhado com o detalhe do pedido; o botão ao lado vem da prop `secondary`, aqui "Voltar ao carrinho") ("Tentar com outro cartão"): valida o cartão com `validatePayment` (`lib/checkout.ts`), tokeniza no Payments (`tokenizeCard`) e chama `retryOrderPayment` (`lib/orders.ts`, `retryOrderPayment` no gateway; sessão vencida vira `SessionExpiredError`, e `VALIDATION`, `NOT_FOUND` e `CONFLICT` viram mensagens); no `202`, a tela volta a "Processando" e acompanha a nova tentativa pelo hub. Esgotadas as tentativas, a tela orienta a fazer um novo pedido. Sem mensagem em 10 s (`PAYMENT_TIMEOUT_MS`) ou se a conexão falhar, mostra "Pendente": o pedido existe e o resultado será enviado por e-mail. Os três textos citam o e-mail do cliente. Fora da recusa com tentativas, a tela oferece "Continuar comprando" e "Ver meus pedidos". O resumo do carrinho (`OrderSummary`) e o do checkout mostram total = soma dos itens, sem frete nem imposto, igual ao `Total` que o Orders registra.
- **Meu cadastro**: a `ProfilePage` (dentro do `RequireAuth`) carrega o cadastro com `useRequest` (`ErrorState` com "Tentar de novo" se o Customers não responder), mostra o e-mail da conta só para leitura e os formulários `BuyerForm` e `ShippingAddressForm`, valida com `validateBuyer`/`validateAddress` e salva com `saveProfile`: "Cadastro salvo." no sucesso, os erros da API nos campos (`address.x` vira o campo `x`) e, com o serviço fora, a mensagem de que não foi possível salvar, mantendo o que foi digitado.
- **Meus pedidos**: a `OrdersPage` (dentro do `RequireAuth`) carrega a primeira página com `useRequest` e acrescenta as seguintes em "Carregar mais" (enquanto `hasMore`), descartando `orderNumber` já exibido (um pedido novo, feito em outra aba, empurraria a lista); cada linha tem foto, número, `OrderStatusBadge`, data, quantidade de itens e total, e leva ao detalhe. Sem pedidos, "Você ainda não fez nenhuma compra" com link para a loja; com o Orders fora, `ErrorState`. A `OrderDetailPage` mostra o pedido como foi comprado (itens com preço unitário, quantidade, subtotal e o desconto só quando é maior que zero, total e endereço) e o texto da situação; `null` da API vira "Pedido não encontrado". Pedido `Pending` acompanha a tentativa atual pelo `watchOrderPayment`, sem prazo, enquanto a página está aberta, e recarrega o pedido no desfecho (o `onChanged` passa por `useEffectEvent`, para o hub não reconectar a cada renderização); se a conexão falhar, avisa que o resultado vai por e-mail. Com `canRetryPayment`, mostra o `RetryPaymentForm`, e o `202` recarrega o pedido, que volta a `Pending` na nova tentativa.
- **Componentes**: `src/components/ui/` contém os primitivos do shadcn (estilo `new-york`, ícones `lucide-react`, configurados em `components.json`). As outras pastas de `src/components/` são organizadas por página (`home`, `product`, `cart`, `checkout`, `layout`, `orders`); `ErrorState` e `LoadingState` ficam na raiz. Use `cn()` de `src/lib/utils.ts` para combinar classes. O import `@/*` aponta para `src/` (`tsconfig.json` e `vite.config.ts`).
- **Estilo**: o Tailwind v4 entra pelo plugin `@tailwindcss/vite` e é configurado via CSS em `src/index.css` (`@import "tailwindcss"`, tokens de tema como variáveis CSS em `oklch`, variante `dark` via classe `.dark`). Use os tokens semânticos (`bg-background`, `text-primary`, `text-muted-foreground` etc.) em vez de cores fixas.
